# Git Workflow

## Purpose

Keep changes reviewable, recoverable, conventionally named, and safe in a frequently dirty monorepo worktree.

## When to use

Use for branch or commit preparation, status cleanup, pull requests, merges, release tags, changelog coordination, or questions about repository history.

## Project-specific rules

- Use short-lived feature/refactor branches and pull requests into the repository's primary branch. CI must pass before merge.
- Follow the scoped commit style shown in `docs/GIT_WORKFLOW.md`, such as `feat(auth): ...`, `test(api): ...`, `feat(admin): ...`, and `ci: ...`.
- Keep commits coherent by responsibility while preserving a complete vertical slice across apps when the contract requires it.
- Run `git status --short` before and after work. Existing modified/untracked files belong to the user unless proven otherwise.
- Never discard, stage, amend, commit, merge, push, tag, or release without the authority implied by the user's request.
- Review lockfile changes generated by `flutter pub get` or npm rather than editing them manually.
- Release tags match `v*` and trigger signed APK, GHCR image, GitHub Release, and deployment automation; treat tag creation as consequential external state.
- Update `CHANGELOG.md` and synchronized component versions for an actual release milestone, not every local patch.

## Best practices

- Inspect `git diff --check`, `git diff --stat`, focused diffs, and relevant untracked files before staging.
- Keep unrelated formatting or generated output out of feature commits.
- Use non-interactive Git commands and explicit pathspecs.
- Split structural refactors from behavior changes when it improves reviewability.
- Record test commands and known pre-existing failures in the handoff or pull request.
- Create annotated release tags only from a clean, tested commit.

## Common mistakes

- Running `git reset --hard`, `git checkout --`, clean operations, or broad deletion over user work.
- Treating an untracked migration/test/Postman file as disposable.
- Committing secrets, local databases, build outputs, `.idea`, caches, or dependency directories.
- Hand-editing lockfiles or generated registrants.
- Creating a release tag just to test a workflow.
- Mixing an application feature, unrelated cleanup, and dependency churn in one opaque commit.
- Claiming a clean result without checking the final status and diff.

## Required workflow

1. Run `git status --short`, identify the current branch, and establish which changes belong to the task.
2. Read `docs/GIT_WORKFLOW.md`, relevant recent commits, and release docs when tagging/releasing.
3. Implement only the authorized scope and keep unrelated work untouched.
4. Run focused checks, then the repository gate appropriate to the change.
5. Inspect `git diff --check`, `git diff --stat`, full relevant diffs, and untracked authored files.
6. If asked to commit, stage explicit paths and use a scoped conventional message.
7. If asked to tag/release, require a clean tested commit, use an annotated milestone tag, and confirm signing/deployment readiness.
8. Report the final branch/status, commits/tags created, checks, and any remaining user changes.

## Files that should never be modified

- Never modify or commit secrets, keystores, local `.env`, Postman Current values, local databases, caches, build output, dependency trees, or IDE state.
- Never hand-edit package lockfile internals or generated Flutter registrants.
- Never rewrite applied migrations or published history to simplify a local task.
- Never discard unrelated tracked or untracked user work.

## Checklist before completion

- [ ] Task-owned changes are distinguished from pre-existing work.
- [ ] Branch and commit structure match the requested scope.
- [ ] Generated, local, secret, and unrelated files are excluded.
- [ ] Format/lint/tests and `git diff --check` were run as appropriate.
- [ ] Any commit message follows the repository's scoped style.
- [ ] Tags/releases were created only with explicit authority from a clean tested commit.
